# Архитектура помощника разработчика дня 31

Приложение отвечает по документации Unity-проекта. Оно не пишет файлы игры,
не запускает Unity, не делает PR-ревью и не использует CRM. Репозиторий
игры монтируется read-only в отдельный MCP-процесс.

## Процессы и модули

client — Vue UI и proxy /api. backend — агент ProjectHelpAgent, RAG,
SQLite и клиенты MCP/Ollama/DeepSeek. project-mcp — Kotlin/Spring Boot
и официальный SDK, endpoint /mcp. ollama — локальные embeddings и генерация.
Веса существующего volume монтируются только для чтения; runtime Ollama
и данные ассистента имеют отдельные volumes. HTTP привязан к 127.0.0.1.

config хранит серверные настройки. llm содержит порты Embeddings/Generator
и ModelGateway. project содержит ProjectGateway, MCP-клиент и wire DTO.
rag — модели, MarkdownChunker, IndexService и Retriever. projecthelp владеет
DTO, политиками и агентом. storage хранит записи; common — ошибки и Jobs.
web переводит HTTP в вызов прикладного сервиса.

Review/Support/Workspace появятся на своих днях. Пустых пакетов заранее нет;
новые домены не наследуют права записи автоматически.

## MCP

SDK выполняет initialize, согласование протокола, tools/list и tools/call.
McpProjectGateway не подменяет MCP обычным REST-вызовом.
Инструменты: get_project_context, get_document_snapshot, list_project_files,
read_project_file, search_project.

Корень задан только серверной конфигурацией. Разрешены README.md,
docs/**/*.md и C# в Assets/Prototype. Проверяются нормализованный путь,
реальная цель ссылки, размер. Git-команды фиксированы в коде;
fsmonitor и optional locks отключены. Произвольного shell tool нет.

В дне 31 обязательный Git-контекст инициирует приложение. Модель не выбирает
дополнительные tools; самостоятельное исследование файлов относится к дню 34.

## Индексация

Построение запускается пользователем. MCP возвращает README и docs
с точными текстами и хешами. Сервер дважды проверяет снимок; индексатор
сверяет его после embeddings.

Markdown делится по заголовкам и группам строк около 1800 символов.
Номера строк относятся к исходнику; CRLF не ломает заголовки.
Это символы, не токены. Длинная строка остаётся целиком; при превышении
явного лимита — ошибка, а не тихое обрезание.

Метаданные: path, section, startLine/endLine, fileHash, chunkId, status.
Research — PROPOSAL_OR_RESEARCH; исторические сводки — MIXED_HISTORY.
Эти пометки не доказывают актуальность каждого предложения.
Явный раздел README «Текущее состояние» имеет CURRENT_STATE и включается
как один видимый контекст версии вместе с релевантной выдачей.
Это помогает отделять текущий ActOne от старой сборки, но не заменяет проверку смысла ответа.
По ссылкам этого раздела добавляется до трёх наиболее релевантных фрагментов
с origin=README_LINK. Это реальные документы, не эталоны ответов. Общее top-K
и бюджет сохраняются. Наличие ссылки не гарантирует актуальность всей страницы.

Ollama /api/embed использует truncate=false. Проверяются digest весов,
число/размерность, конечность и ненулевая норма векторов. Публикация READY
атомарная; предыдущий готовый индекс сохраняется при ошибке нового.

## Алгоритм запроса

1. HelpInputPolicy проверяет вопрос, провайдера и UUID. /help — команда;
   обычный текст также принимается как вопрос этому агенту.
2. В SQLite сохраняется RUNNING ход с вопросом.
3. MCP читает текущую ветку, SHA, dirty и fingerprint README/docs игры.
4. Проверяются SHA/хеши и identity embedding-модели. Если игра изменилась,
   запрос продолжается по прежнему READY индексу с предупреждением STALE_INDEX.
   Смена embedding-модели по-прежнему блокирует поиск до переиндексации.
5. Локальный embedding вопроса, dense cosine и лексический RRF.
   До 7 фрагментов, cosine не ниже 0.20, до 14000 символов источников.
   Порог — не вероятность качества и не универсально оптимальная настройка.
6. Модели передаются вопрос, live-контекст, отдельный контекст версии индекса,
   предупреждения об устаревании, источники и до трёх прошлых
   завершённых ходов (ответы до 2000 символов). Полная история хранится,
   но это ограниченный conversational RAG, не долговременная память.
7. Один явно выбранный провайдер без retry/fallback. При пустой выдаче
   retrieval возвращает UNKNOWN без генерации.
8. Ответ и точный API usage сохраняются до завершающей MCP-проверки.
   Её сбой не уничтожает уже полученный ответ.
9. HelpOutputPolicy проверяет ID ссылок. IDS_VALID не означает
   семантическую истинность. MISSING/INVALID явно видны в UI.

Повтор UUID с тем же содержимым возвращает сохранённую запись; другое
содержимое даёт конфликт. После restart незавершённые операции становятся
INTERRUPTED, не запускаются заново и не создают повторные расходы.

## Хранение и UI

SQLite разделяет kind: index, help-chat, help-turn. Ход хранит вопрос,
ответ, источники, события MCP, snapshot-контекст, статус и usage.
Новые ходы отдельно сохраняют indexContext и warnings. История старого
формата читается с null/пустым списком; её результаты не переписываются.
Live SHA описывает checkout на момент вопроса, а SHA/fingerprint индекса —
версию найденных фрагментов. UI и MD показывают предупреждение конкретного
ответа даже после последующего обновления базы. Обновление индекса вручную
остаётся необязательным, автоматическая переиндексация не запускается.
Вектора не отправляются браузеру. HTML модели/документов не исполняется.
MD-экспорт использует буквальные fenced-блоки без вызова LLM.

Одна ресурсоёмкая работа за раз: BUSY вместо скрытой очереди.
Polling читает БД, не повторяет генерацию. Приложение рассчитано
на одного локального пользователя; авторизации пока нет.
