# Архитектура поддержки игроков дня 33

Ветка ai-challenge-day-33 от локального checkpoint 086f611 дня 32.
Поддержка — отдельный домен ассистента. Игра остаётся источником знаний,
но её код, ветки и файлы не изменяются. Фоновая обработка PR отключена.

## Владение данными

support-mcp — отдельный Kotlin/Spring Boot сервис. Он единственный владелец
JSON-каталога в volume support-data. REST API принимает команды формы,
MCP предоставляет только чтение. Backend не получает файловый mount
хранилища и не записывает те же файлы вторым способом.

users.json содержит два вымышленных профиля. tickets/UUID.json содержит
обращение, обстоятельства и всю переписку: вопросы, ответы, статусы,
снимки MCP-контекста, источники FAQ, метрики и ошибки.
Support-contracts — общие транспортные DTO, без Spring, LLM или persistence.

Класс JsonTicketRepository защищает каталог process-lock. Второй процесс
не начинает запись в тот же каталог. Запись одного агрегата выполняется
через временный файл, force и atomic move. Поддерживается один владелец,
не распределённое JSON-хранилище. Ошибка чтения не сбрасывает данные.
Обновление результата использует revision, чтобы запоздавший ответ
не перезаписал завершённый или прерванный ход.

## Создание обращения

Форма Vue передаёт тему, описание, сборку, платформу и UUID через backend.
SupportAgent проверяет форму обращения через контракт владельца данных.
SupportTickets нормализует команду; JsonTicketRepository проверяет доступ
и сохраняет JSON атомарно. В этой операции нет LLM и embeddings.
Повтор UUID с теми же полями возвращает существующее обращение;
другое содержимое с тем же UUID вызывает конфликт.

«Вопрос по FAQ» явно создаёт диалог типа QUESTION. Обычное обращение имеет
тип ISSUE. Обе переписки хранятся одинаково; модель не создаёт тикеты сама.

## Ответ на вопрос

1. Backend проверяет существование обращения и соответствие demo-профилю.
2. SupportAgent сохраняет вопрос RUNNING в JSON до вызова модели.
3. McpSupportContext открывает настоящий Streamable HTTP сеанс:
   initialize, tools/list и tools/call:get_ticket_context.
4. Support MCP повторно проверяет владельца. В ответ входят профиль,
   описание, заявленная сборка, платформа и до трёх последних завершённых
   обменов. Полная история остаётся в JSON; в LLM отправляется ограниченный хвост.
5. SupportKnowledge выполняет локальный retrieval по отдельному FAQ-индексу.
   Текст вопроса и обстоятельства используются как поисковый запрос,
   но не добавляются в индекс.
6. Выбранная модель получает системную политику поддержки, вопрос,
   MCP-контекст и найденные фрагменты. Другие обращения не передаются.
   Из хвоста истории в prompt остаются уточнения игрока; прежние модельные
   ответы исключаются, чтобы не закреплять ошибочную диагностику.
7. Ответ, API usage, источники и журнал MCP сохраняются в JSON.
   UI показывает сохранённый результат через GET polling, без повторной генерации.

MCP-контекст обязателен для сценария: его получение выполняет агентское
приложение, не случайное решение модели. Модель не может изменить user_id,
выбрать чужой тикет или вызвать инструменты записи. При недоступном MCP
вопрос и диагностика сохраняются, LLM не вызывается.

## База знаний

В backend/resources/support-knowledge находятся четыре Markdown-документа:
обзор, управление, сохранения и безопасная диагностика. Они подготовлены
по рабочему снимку игры от 16.10.2026. origin.json фиксирует пути и SHA-256
исходных документов; это не опубликованный релиз и не обещание актуальности
изменяющейся рабочей папки.

Индекс создаётся явно кнопкой: MarkdownChunker, локальные embeddings
qwen3-embedding:0.6b, SQLite support-index, hybrid retrieval.
Fingerprint документов и identity embedding-модели проверяются перед поиском.
Индексы /help, PR review и support разделены.
Тикеты, профили и переписка в общий корпус не попадают.

Пустая выдача приводит к уточнению без LLM. SupportOutputPolicy не пропускает
ответ без ссылок, с несуществующим ID или новым абсолютным/AppData-путём,
которого нет в источниках. Такой текст сохраняется как candidateAnswer,
UI показывает его только в раскрываемом непроверенном черновике, статус UNKNOWN.
Повторной генерации нет. Проверка ссылок фиксирует существование ID,
но не доказывает правильность диагноза или каждого шага.
Факты о продукте опираются на FAQ, обстоятельства тикета — слова игрока.

## Доступ и эксплуатация

Это локальный демонстрационный сервис с вымышленными данными.
X-Demo-User задаёт выбранный профиль, а не аутентифицирует реального человека.
Проверка владельца не даёт читать чужой тикет в рамках выбранного профиля,
но переключатель позволяет намеренно сменить demo identity.
Для настоящих пользователей нужны login/session и identity из security context.

Support MCP не публикует порт на хост и доступен только внутренней Docker-сети.
UI и backend привязаны к loopback. Нет shell tool, доступа к реальным
сохранениям игры, настоящей CRM или автоматического изменения кода.
Ключ DeepSeek остаётся на backend; скрытого fallback и платных retry нет.

Один общий Jobs-слот защищает GPU и генерации. После restart RUNNING становится
INTERRUPTED; запросы к модели не возобновляются автоматически. История и индексы
сохраняются в volumes. down -v удалит данные, поэтому для остановки нужен stop.
JSON хранится открытым текстом локально; настоящие персональные данные не вводите.

## Пауза дня 32

Compose ветки 33 задаёт REVIEW_RUNTIME_ENABLED=false. Выключатель запрещает
discover, processNext, ручную синхронизацию, новые анализы и публикации,
даже если в SQLite осталась очередь. Сохранённые отчёты доступны для чтения.
GitHub workflow в игре не меняется: он может создать artifact при новом PR,
но локальный ассистент его не забирает. Возобновление дня 32 — отдельное действие.
