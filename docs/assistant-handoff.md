## День 31 и критерии приёмки

Задание: подключить документацию проекта через RAG, проект через MCP
и реализовать `/help`, отвечающий на вопросы о проекте.

Обязательный минимум курса:

1. README и папка docs игры реально входят в индекс с embeddings.
2. Через MCP получается текущая Git-ветка игры.
3. `/help` отвечает о структуре проекта, используя документацию
   и актуальный контекст.

Нам нужны проверяемые источники: путь, раздел, диапазон строк,
`chunk_id`, версия Git и хеш файла. UI должен показывать ответ,
фрагменты и результат MCP, чтобы различать знания из RAG и актуальные
данные проекта. Это выбранный подход к демонстрации, а не замена
минимальных требований дополнительными фичами.

Ветка ассистента не является веткой игры. MCP должен читать Git именно
разрешённого репозитория игры; при detached HEAD сообщать этот факт
и SHA, а не придумывать имя ветки. При смене версии источников явно
обнаруживаем устаревший индекс и выбираем поведение до реализации.

## День 32 и критерии приёмки

Задание: автоматический пайплайн на PR получает diff и изменённые файлы,
использует RAG по документации и коду, возвращает текст ревью:
потенциальные баги, архитектурные проблемы и рекомендации.

Предлагаемый результат: сохранённый Markdown-отчёт и итог в PR.
У замечания есть категория, важность, файл/строка, обоснование,
последствие и предложение исправления. Проверяем, что указанные
пути, строки и источники существуют; это ещё не доказывает истинность
каждого замечания модели.

Workflow размещается в репозитории игры, версия анализатора приходит
из репозитория ассистента. Нужно закрепить версию runner, `base SHA`
и `head SHA`, обработать пагинацию/недоступный patch/бинарные файлы
и явно отмечать неполный анализ. Документацию базовой версии и код
проверяемой версии различаем; изменение документации в PR само
по себе не становится новой системной инструкцией или принятым правилом.

Повтор/обновление PR не должно оставлять противоречивые результаты
без привязки к SHA. Наличие замечаний не равно провалу сборки:
блокирующую политику согласуем отдельно. Автоматические изменения
кода, commit исправлений и merge не входят в текущий объём.

## Предлагаемая структура приложения

Начинаем с модульного приложения, а не множества микросервисов.
Ответственности: адаптеры LLM, индексация и retrieval, MCP/контекст проекта,
use cases Help и Review, хранение результатов, web API и CI CLI.
Help и Review переиспользуют общие возможности, но имеют собственные
инструкции, входные ограничения и проверку ответа. Judge добавляем
только при конкретной необходимости, не встраиваем платный judge
в каждый запрос по умолчанию.

Для `/help` backend получает актуальный контекст через MCP, подбирает
документы через RAG и передаёт их с вопросом LLM. Обязательные данные
не должны зависеть от случайного решения модели вызвать tool.
Дополнительное чтение файлов можно выполнять ограниченным tool loop:
модель предлагает вызов, приложение проверяет и исполняет его через MCP.
Точный контракт инструментов и предел итераций ещё предстоит выбрать.

Для ревью тот же модуль анализа работает из CLI в GitHub Actions.
Предлагаемый старт: embeddings/retrieval на runner, генерация через
DeepSeek и ключ из GitHub Secrets. Нельзя рассчитывать, что облачный
runner сможет обращаться к домашней Ollama. Unity-тестирование и
AI-ревью — отдельные jobs; анализ текстовых исходников не требует Editor.

У следующих дней пока нет требований. Новую функцию добавляем в отдельный
use case/домен с собственными настройками и тестами, не копируем весь
ассистент и не проектируем заранее платформу на сотни агентов.

## Наработки и уроки прошлых заданий

В старом `ai-chat` на ветке `ai-challenge-day-28` есть Kotlin RAG:
[описание классов](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-28/local-llm/backend/src/main/kotlin/dev/aichallenge/local/rag/README.md).
Полезны порты embeddings/generation, проверка identity embedding-модели,
hybrid retrieval, сохранённый snapshot контекста, независимые статусы
провайдеров и экспорт результатов. Привязки к Warhammer, TXT-only import
и эвристику BOOK_OPENING не переносим как универсальную архитектуру.
Историю Git старого репозитория целиком не сливаем в новый.

Для документации и C# нужны подходящие разбиение и метаданные строк.
Сцены, префабы и ScriptableObjects Unity требуют отдельного решения:
обычная индексация YAML не доказывает понимание связей GUID/fileID.

Из живых проверок RAG: `COMPLETED` означает завершённый вызов, не качество;
`VALID` у ссылки — существующий ID, не доказательство утверждения.
Отказ при неоднозначном названии может быть осторожным поведением,
а уверенный ответ — неподтверждённой догадкой. Проверяем точные вопросы,
варианты названий и достаточность источников. Similarity не является
вероятностью правильности; локальные оценки токенов не смешиваем
с фактическим usage API.

Не воспроизводим прежние проблемы: скрытые retries/fallback в облако,
необъяснённые лимиты ответа, потеря уже полученных результатов,
неустойчивое чтение DTO без понятной ошибки или UI-статусы,
не соответствующие фактическому состоянию backend.

## Безопасность и эксплуатация

- MCP только read-only, с фиксированным корнем игры, разрешёнными
  операциями, проверкой путей и ограничениями объёма/времени.
  Произвольный shell и произвольный filesystem root не предоставляем.
- Ключи остаются на backend/в CI Secrets. Не индексируем `.env`,
  лицензии Unity, Git-credential данные, кеши, сборки, веса и изображения.
- Код PR, документация и tool output являются недоверенными данными.
  Не исполняем код PR с доступом к секретам и не воспринимаем его
  текст как полномочия для новых действий.
- Начальный AI-пайплайн предлагается для доверенных собственных PR.
  Fork PR и доступ к секретам проектируем отдельно без небезопасного
  запуска через `pull_request_target`.
- Нужны ограничения стоимости, контекста, числа tool/LLM-вызовов
  и понятный отчёт о том, что не удалось проверить.
  Бюджеты API прошлых дней не являются разрешением тратить их на новый проект.
- Runtime-данные и индексы остаются локальными/в выбранном хранилище,
  не попадают в публичный Git. Диагностика не выводит секреты.
- Новые Docker-проекты, порты и volumes отделяем от старых.
  Ничего не удаляем из Docker и не меняем глобальный Git ради этого проекта.
