# Локальное автоматическое ревью PR

Согласованный вариант дня 32: GitHub Actions создаёт JSON-задание,
локальный backend забирает его через исходящий HTTPS и выполняет ревью.
Публичного входа, туннеля и self-hosted runner нет. Игра не зависит от агента.

## Цепочка

1. PR открыт или обновлён в ai-challenge-game.
2. Workflow ai-review.yml сохраняет review-request.json с repository, PR,
   base/head SHA и runId. Его успех означает создание задания, не готовое ревью.
3. Локальный poller раз в 30 секунд проверяет доверенный workflow.
4. Задание регистрируется в SQLite с ключом repository/PR/base/head/версия
   анализатора/провайдер. Повторное обнаружение не создаёт вторую генерацию.
5. ReviewUseCase получает diff и разрешённые документы/C# точных версий
   через GitHub API. Рабочая папка игры не переключается и не изменяется.
6. Локальные embeddings и retrieval подбирают документацию базовой версии
   и код проверяемой версии. Они не используют произвольный старый индекс /help.
7. DeepSeek Pro получает diff и найденные фрагменты. Код PR не исполняется.
8. Ответ валидируется, сохраняется до публикации и отображается в UI.
9. GitHubPublisher публикует сохранённый отчёт. Ошибка публикации не повторяет LLM.

## Границы домена

review владеет моделями, политиками, заданиями, результатами и состояниями.
GitHubGateway — узкий внешний контракт, API-адаптер скрывает HTTP и секреты.
ReviewUseCase — один анализ для worker и ручного запуска из UI.
ReviewRepository использует общие атомарные операции RecordStore.
Poller занимается обнаружением/запуском, а не генерацией промпта.
Общие Embeddings/Generator и MarkdownChunker переиспользуются; /help сохраняется.

## Состояния и повторы

QUEUED → INDEXING → ANALYZING → REPORT_READY → PUBLISHING → COMPLETED.
Возможны FAILED, INTERRUPTED, SUPERSEDED. PARTIAL — характеристика покрытия,
не синоним отсутствия замечаний. Новая версия PR получает отдельное задание.

После restart INDEXING можно безопасно повторить, ANALYZING становится
INTERRUPTED без автоматического платного повтора. REPORT_READY/PUBLISHING
с сохранённым отчётом можно допубликовать без генерации. Не обещаем
exactly-once вызов внешней модели при обрыве сети в неопределённый момент.
Запись задания и захват состояния атомарны в SQLite. Сетевые вызовы не
выполняются внутри DB-транзакции. При публикации используется устойчивый
маркер отчёта; проверяется текущий head PR.

## Контекст и ограничения

Вход фиксирует base/head SHA. Документация базы — исходные правила,
документация из PR — предлагаемое изменение, а не системная инструкция.
C# разбивается с сохранением строк; это текстовый анализ, не компилятор C#.
Сцены, prefab, изображения, сборки, секреты и зависимости не индексируются.
Неподдержанные/слишком большие файлы и недоступный patch отражаются в покрытии.
Пути/строки замечаний должны существовать в diff; ссылки — в выбранном RAG.
Проверка формата не доказывает семантическую истинность замечания.

## Авторизация

Вначале допускаются только собственные PR Vetka63 внутри выбранного repo,
не fork PR. Artifact — недоверенные данные, а не произвольный shell/URL.
После чтения перепроверяются repo, workflow, PR и SHA через GitHub API.
Токен fine-grained хранится локально в .local/day32/github-token, монтируется
в backend read-only. Actions Read, Contents Read, Pull requests Read and write.
DeepSeek-ключ остаётся в прежней backend-конфигурации, не в GitHub workflow.
В UI и логи не возвращаются ключи, сырые HTTP-ошибки или заголовки.
Автоматика включается явно в UI; остановка ПК останавливает анализ.
Artifact имеет ограниченный срок хранения; poller сверяет также актуальные
открытые PR, подтверждённые успешным запуском workflow, чтобы восстанавливать
пропуски. Ограничения страницы/покрытия видны, не маскируются полным успехом.

## Этапы

Домен и локальные тесты → GitHub-адаптер/worker → UI → workflow-шаблон
и инструкция токена → автоматические проверки → согласованная живая проверка
реальных PR → руководство для видео. Commit/push/PR/merge — отдельной командой.
Дни 33–34 не реализуются в этом этапе.
