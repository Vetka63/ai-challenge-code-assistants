# Файловый ассистент дня 34

Ассистент получает цель, самостоятельно выбирает поиск и чтение исходников,
затем сохраняет новый Markdown-документ или предложение изменения с unified diff.
Основная игра не изменяется. Браузер и CLI используют одного агента в существующем backend.

## Состав приложения

- Kotlin backend: домен workspace, HTTP API, агентский цикл и история SQLite.
- Workspace MCP: отдельный внутренний процесс, владелец файловых снимков и артефактов.
- Vue: постановка цели, выбор модели, журнал, прочитанные диапазоны, документы и diff.
- Kotlin CLI: команды к тому же HTTP API, без собственных ключей и второй реализации агента.
- Project MCP и Support MCP сохраняют прежние функции. Review runtime дня 32 выключен.

В backend домен workspace разделён на api, service и gateway. DTO файловой границы
находятся в workspace-contracts. Workspace MCP содержит storage, api и mcp.
Общие адаптеры модели и SQLite переиспользуются без переноса правил агента в common.

## Владение данными

Игра монтируется в Workspace MCP как read-only. Снимок создаётся явной командой
из README.md, docs/**/*.md и C# в AsciiArena/Assets/Prototype. Другие пути недоступны.
Содержимое читается повторно при создании: если набор или тексты изменились,
операция возвращает SOURCE_CHANGED, а не смешивает две версии.

Snapshot содержит точные тексты, SHA-256 каждого файла и общий fingerprint.
Это снимок рабочей копии, включая разрешённые незакоммиченные файлы, не утверждение
о соответствии конкретному Git-коммиту. Следующие запросы читают только snapshot.
Обновление игры не подменяет источники старого запуска.

Volume workspace-data принадлежит только Workspace MCP. Backend не монтирует его
вторым писателем. Эксклюзивный файловый lock не допускает двух владельцев.
JSON записывается через временный файл, force и atomic rename. Повреждённая запись
не заменяется пустой. SQLite backend хранит отдельный kind workspace-run.
LLM и сетевые вызовы не выполняются внутри транзакции SQLite или файловой блокировки.

## Инструменты

Настоящий MCP SDK выполняет initialize, tools/list и tools/call.
Backend проверяет имя сервера game-workspace и разрешённый набор инструментов.

1. list_files возвращает пути, хеши, число строк и пагинацию.
2. search_files выполняет буквальный поиск по нескольким файлам с total и hasMore.
3. read_file возвращает до 160 строк и регистрирует подтверждение чтения.
4. create_document сохраняет новый Markdown и diff добавления.
5. propose_file_change сохраняет полный новый Markdown и diff изменения.

snapshot_id и run_id привязывает backend: модель не может подменить scope.
Схемы запрещают неизвестные поля; сервер повторно проверяет типы, диапазоны и пути.
Произвольного shell, URL, исполнения C#, доступа к .git, .env и Unity-ассетам нет.

Перед сохранением нужны минимум три разных действительно прочитанных исходника.
Сервер сам строит evidence по подтверждениям read_file, модель не передаёт этот список.
Для полной замены существующего документа нужны все его строки,
точный base_hash и изменившееся содержимое. Подтверждения другого запуска не подходят.
Явно помеченные исторические блоки до следующего заголовка защищены от изменения.
Правило распознаёт настроенные русские маркеры, например «Следующие абзацы описывают историю».
Это структурная защита известных обозначений, не универсальная семантическая классификация истории.
Исходные единообразные CRLF сохраняются, чтобы не переформатировать весь документ.
Это структурная проверка происхождения, не доказательство истинности каждого вывода LLM.

## Агентский цикл

Пользователь выбирает снимок, модель и цель. Backend сохраняет UUID запуска до генерации.
Модель получает инструкции и схемы инструментов, но не заранее заданный список файлов.
Она предлагает tool calls. Приложение проверяет их, выполняет через MCP,
добавляет ответы с корректными tool_call_id и снова вызывает модель.
Новый документ возникает только после успешного инструмента сохранения.

DeepSeek и Ollama используют настоящий tool calling. Обычный Generator прежних дней
остаётся отдельным контрактом. Провайдер выбирается явно, без облачного fallback.
Для каждого шага сохраняются модель, фактические usage, finish reason и время.
Журнал показывает операции, а не скрытые рассуждения модели.

Один запуск ограничен 24 LLM-шагами, 64 tool calls и восемью calls за один ответ.
Размер сериализованного контекста ограничен 60000 символов для LOCAL и 180000 для DEEPSEEK.
Это защитные бюджеты агента, не точный подсчёт токенов и не контекстное окно модели.
Ollama запрашивает num_ctx=16384. Скрытого повторного запроса нет.

COMPLETED означает сохранённый артефакт и минимум три прочитанных файла.
ANALYZED означает текстовый анализ без готового изменения. FAILED сохраняет
ошибку и частичный результат. После рестарта RUNNING становится INTERRUPTED без повторной оплаты.
Эти статусы не являются автоматической оценкой качества текста.

Завершённые COMPLETED/ANALYZED ходы можно продолжать с сохранённым transcript
в том же снимке. Ошибочный или незавершённый transcript не отправляется модели повторно.
Новый ход получает новый UUID и заново подтверждает источники для нового артефакта.

## Артефакты и повтор

Workspace MCP сохраняет JSON commit record, отдельные .md и .patch.
Именованный документ также находится в outputs/ARTIFACT_UUID/предложенный-путь;
это отдельный каталог артефакта, не изменение baseline снимка.
Идентификатор артефакта зависит от snapshot, run, пути и хеша нового текста.
Повтор того же сохранения возвращает прежний артефакт. Производные .md/.patch
восстанавливаются из JSON при повторе, если сбой произошёл после commit record.
При потере подтверждения вызова backend читает уже сохранённые артефакты, не повторяет генерацию.

Diff строит сервер из точного baseline и предложенного содержимого.
Формат полной замены проще локальных hunks; перед применением вне приложения
нужно проверить исходный хеш и git apply --check на подходящей копии.
Для побайтового сравнения вне репозитория в Windows используйте
git -c core.autocrlf=false apply: глобальная настройка Git может преобразовать LF в CRLF.
Применение к основной игре, автоматические commit, push и PR не входят в день 34.

Повтор POST /runs с прежним UUID и теми же параметрами возвращает сохранённый запуск.
Другие параметры с тем же UUID дают ID_CONFLICT. Новый UUID означает новую работу и новые LLM-вызовы.
Повторяемость сценария означает одинаковые исходники и проверяемый результат,
а не гарантированно одинаковый текст модели.

## Интерфейсы

UI доступен по #workspace и #workspace/RUN_UUID. Polling читает сохранённое состояние
каждые 1.5 секунды только во время RUNNING и не вызывает LLM.
CLI использует /api/workspace/snapshots, /runs и экспорт артефактов.
Ключи остаются в backend. Браузер не нужен для терминального запуска.
Закрытие браузера или CLI не равно отмене задачи на backend.

## Границы качества

Поиск текстовый, не компиляторный анализ C# и не разрешение Unity GUID/fileID.
Файл, найденный поиском, не считается полностью прочитанным.
RAG дня 31 не является обязательным условием работы Workspace: нужны текущие файлы
снимка. Общие архитектурные документы агент может найти и прочитать через tools.
Ассистент не запускает Unity-тесты и обязан обозначать границы своего анализа.
