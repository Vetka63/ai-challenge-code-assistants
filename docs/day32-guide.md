# Запуск и проверка дня 32

Ветка ai-challenge-day-32 создана от c728c7a дня 31. Приложение остаётся
локальным: http://localhost:8683/#reviews. Старый чат /help доступен отдельно.
План и алгоритм: [архитектура](day32-architecture.md).
Настройка секрета: [GitHub токен](day32-github-token.md).

## Подготовка

1. Запустите Docker Desktop. Вес qwen3-embedding:0.6b берётся из прежнего
   read-only volume Ollama. Unity, self-hosted runner и входящие порты не нужны.
2. Создайте и сохраните fine-grained GitHub-токен по отдельной инструкции.
3. Запустите scripts/Start-Day32.ps1 -Build. При импорте существующего
   DeepSeek-ключа передайте KeyFile и KeyVariable, как в Start-Day31.
   Весь чужой .env не импортируется. Имя Compose-проекта и volume сохранены
   ради существующей истории. Токен не входит в build context.
4. В UI откройте «Ревью PR · день 32», проверьте подключение.
5. Автоматику оставьте выключенной до подготовки workflow и тестовых PR.

## Подключить workflow к игре

Шаблон: integrations/github/ai-review.yml. Его нужно разместить в
ai-challenge-game/.github/workflows/ai-review.yml и опубликовать согласованным
коммитом. Для реального ревью в GitHub должна быть опубликована версия
документации и C# игры. Незакоммиченная рабочая папка не является версией PR.
Публикация, создание PR и merge выполняются отдельной командой пользователя.
Изменения игры, которые ведутся параллельно, не следует коммитить автоматически.

Workflow не делает checkout и не запускает содержимое PR. Он записывает
JSON из GITHUB_EVENT_PATH и публикует artifact ai-review-request на 14 дней.
Только собственные PR внутри repo, без fork. Привязка upload-artifact — SHA.
Успех workflow означает «задание создано», не «код проверен».

## Сценарий для видео после настройки GitHub

1. В UI покажите repo, «Токен сохранён», успешную проверку подключения.
2. Включите автоматику.
3. Откройте тестовый PR с одним заранее известным нарушением фактического
   правила игры. Не вводите дефект в рабочий main; используйте тестовую ветку.
4. В GitHub Actions покажите «Request local AI review» и созданный artifact.
5. В течение примерно 30 секунд плюс время загрузки GitHub появится задание
   в UI. Анализ займёт дополнительное время. Покажите точные base/head SHA.
6. Дождитесь отчёта: итог, категория BUG/ARCHITECTURE/RECOMMENDATION,
   изменённая строка, основание, рекомендация, фактические RAG-источники.
7. Покажите комментарий в PR. SHA в нём должен совпадать с проверенным.
8. Исправьте дефект новым коммитом: появится новое задание для нового SHA.
9. Скачайте MD и перезапустите backend без удаления volumes.
   Отчёт должен остаться. Неопределённый ANALYZING после сбоя становится
   INTERRUPTED и не повторяется платно без явного действия пользователя.
10. Отдельно проверьте корректное изменение: отсутствие замечаний допустимо.
    Ассистент не должен выдумывать баг ради демонстрации.

## Ручной запуск и ошибки

Ручной запуск по номеру PR использует тот же ReviewUseCase. Флажок публикации
изначально выключен. Повтор регистрации одной версии возвращает прежнее
задание. REPORT_READY означает готовый локальный отчёт, COMPLETED — опубликованный.
Повтор публикации сохранённого отчёта не обращается к LLM. Новый платный
анализ после ошибки запускается только отдельной явно подписанной кнопкой.

Есть лимит 20 попыток генерации ревью за 24 часа; ошибки модели тоже
учитываются как попытки. Polling и GET состояния не тратят LLM-токены.
Чтение repo не доказывает права на комментарии. Ошибки 401/403/404 показаны
без сырых тел/секретов. Для ревью применяются публичные версии GitHub:
день 31 со старым индексом /help не подменяет версию PR.

Размеры ограничены: до 300 изменённых файлов, diff до 18000 символов,
до 100 релевантных файлов на сторону и до 1 млн символов корпуса,
до 1500 чанков. Отобранные RAG-источники имеют отдельный бюджет retrieval.
Неподдержанные и пропущенные файлы перечисляются; PARTIAL не равно полной
проверке. Сцены и prefab не анализируются как семантика Unity.

Проверяются последние 300 успешных запусков доверенного workflow.
При отсутствии/истечении artifact возможна реконструкция задания только
по связанной записи PR этого запуска и совпадающему head SHA. Это не
бесконечная очередь GitHub; неразрешённые пропуски видны в диагностике.

## Автотесты

    .\gradlew.bat :backend:test :project-mcp:test
    cd client
    npm ci
    npm test
    npm run build

Обычные тесты бесплатные и не пишут в GitHub. ReviewLiveTest запускается
только с DAY32_LIVE=true, существующим ключом и явным каталогом результатов.
Он проверяет три синтетических diff через настоящие embeddings/DeepSeek,
но не является доказательством доставки настоящего PR через Actions.
